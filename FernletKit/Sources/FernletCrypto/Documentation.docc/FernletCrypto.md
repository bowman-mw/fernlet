# ``FernletCrypto``

Layer-0 sealing primitives: the ChaChaPoly column-encryption helper the sealed private stores use to encrypt sensitive fields at rest.

## Overview

FernletCrypto is the smallest module in the FernletKit package — built around ``ColumnCrypto`` and ``DeviceBindingID``, with the domain-separation purpose namespace beside them and, since Phase 1 of the crypto-standardization plan, the format-migration protocol family described below, which shares the target for layering reasons rather than subject-matter ones — and it exists to give the sealed ("S3") stores one shared, well-audited way to encrypt individual sensitive columns. A column here is one field of one Core Data row: a journal entry's text, its emotion list, a menstrual narrative's note and symptom flags, an intimacy log's note, a worry-box entry. Each of those is sealed independently with ChaCha20-Poly1305 (CryptoKit's `ChaChaPoly`) and stored as one opaque blob in a single binary attribute of the local-only private Core Data store. Two at-rest generations coexist: the legacy form is the sealed box's raw `combined` bytes (nonce ‖ ciphertext ‖ tag); the **device-bound v2** form — every new write, when a binding ID is available — prefixes a version byte and seals with this install's ``DeviceBindingID`` as ChaChaPoly additional authenticated data, so the ciphertext itself refuses to authenticate on any other install. Opens are dual-path (v2-with-AAD first when the prefix is present, then the legacy no-AAD open), so pre-binding rows keep opening and are progressively rebound by routine re-seals; when no durable binding ID exists, sealing falls back to the legacy form — binding is defense-in-depth, never a gate (see `Docs/Verifiability.md` §4, and `Tests/FernletTests/ColumnCryptoDeviceBindingTests` for the pinned behavior). The open side additionally distinguishes an *absent* binding row from a *failed* keychain read (``DeviceBindingID/currentForOpen()``): a v2 blob that cannot be opened during a transient keychain error throws the retryable ``DeviceBindingID/ReadError`` rather than a spurious authentication failure, so an outage degrades to "try again" instead of reading as corrupted data.

The central concept is the two-level key hierarchy. A single 256-bit **content key** protects the whole private area; it is minted, wrapped under a passcode-derived key, and vended by `FernletLockService` (in the `FernletLock` module), which returns it only while the user has unlocked the private area. ``ColumnCrypto`` never sees that lifecycle — every seal/open call receives the content key as a parameter and derives a per-column **subkey** from it on the fly, via HKDF-SHA256 with the instance's `ColumnCrypto.label` as the domain-separating `info` input. Nothing in this module stores key material, caches derived keys, or touches the keychain; it is a pure, stateless value type.

The label is what keeps different kinds of ciphertext cryptographically isolated even though they share one content key. Four repositories each own one instance with a fixed label: `JournalNarrativeRepository` ("journal-narrative") and `WorryNarrativeRepository` ("worry-box") in `PrivateMemoryStore`, and `MenstrualNarrativeRepository` ("menstrual-narrative") and `IntimacyLogRepository` ("intimacy-log") in `PrivateHealthStore`. Because HKDF is deterministic, a label is part of the at-rest data format: ciphertext sealed under one label can never be opened under another, so changing a repository's label (or the derivation itself) without a migration orphans all existing rows. Opening also fails — with a thrown CryptoKit authentication error — for truncated or tampered blobs and for data sealed under a different content key, which is exactly the fail-closed behavior the sealed stores rely on.

In the package dependency graph (see `FernletKit/Package.swift`), FernletCrypto sits at Layer 0: it imports only CryptoKit, Foundation, and Security and declares **no** in-package dependencies (``DeviceBindingID`` talks to the keychain through direct Security-framework calls precisely to preserve that zero-dependency layering). Its position relative to the S3 privacy wall is "on the protected side by usage": every importer is a protected-side target (the sealed stores `PrivateHealthStore` and `PrivateMemoryStore`, plus `PrivateStoreCore`, `PrivateMediaStore`, `FernletLock` and `ProximityKit`), and **neither walled consumer (`AIProviders`, `CloudKitSync`) lists it as a dependency** — so under the `DIAGNOSE_MISSING_TARGET_DEPENDENCIES=YES_ERROR` enforcement, walled code cannot even name these types. That last half is what makes this module, and not `FernletFoundation`, the right home for the migration protocols below. Two deliberate non-users of ``ColumnCrypto`` *itself* are worth knowing: `PrivateMediaStore` seals photos through CryptoKit directly with its own keychain key, and `FernletLock` wraps/unwraps the content key with its own `FernletLockCrypto` helpers — both still import this module, for the domain-separation purpose namespace (`CryptographicPurpose` / `FernletCryptoPurpose`) and, in `PrivateMediaStore`'s case, now the migration protocols too; neither for column sealing. The HKDF column-key derivation itself lives in one place — ``ColumnCrypto``'s internal `deriveColumnKey` static — which the crypto unit tests characterize directly (via `@testable import`), including a pinned known-answer vector.

The module's one non-sealing concern is the **format-migration protocol family** — ``FormatMigrator`` with its two companions ``FormatMigrationPassResult`` and ``FormatMigrationLatching`` — added by Phase 1 of `Docs/Plan-Crypto-Standardization-2026-08-27.md`. It is the shape every at-rest cryptographic format migration in the app has to have: **scan → convert → latch**, in bounded, resumable, idempotent passes, with the shared `run(maxPasses:)` loop and `isComplete` living in a protocol extension so no conformer re-spells them. Nothing about the contract was invented here — it was lifted from `PrivateMediaStore`'s shipping `OwnPhotoKeyMigrator`, which became the first conformer and deleted its own `run`/`isComplete` in favour of the shared pair, with the untouched `OwnPhotoKeyMigrationTests` standing as the proof that the generalization is behavior-preserving. The latch is fail-closed by contract: it may be set only by a pass that converted nothing, failed nothing, and could classify everything, because every latch in this family gates an irreversible step (dropping a legacy reader, binding a key) whose cost falls on bytes the pass never saw — "I could not look" must never latch. That this lives *here* rather than in `FernletFoundation`, the other reachable Layer-0 home, follows from the paragraph above: `CloudKitSync` imports `FernletFoundation`, and machinery whose whole purpose is to touch sealed corpora must stay unnameable by walled code, whereas every module that will conform in Phase 2 — `PrivateMediaStore`, `PrivateStoreCore`, `FernletLock`, `ProximityKit`, and the app target — already depends on this zero-dependency target for its sealing primitives, so no conformer needs a new dependency edge to reach it.

Concurrency: the target declares `defaultIsolation(MainActor.self)` in `Package.swift`, but ``ColumnCrypto`` is explicitly `nonisolated` — it must be callable synchronously from the `NSManagedObjectContext.performAndWait` closures of the nonisolated sealed-store repositories, where a MainActor-isolated call would be illegal under Swift 6. Each repository constructs and owns its own instance, so the value never needs to cross an isolation boundary. The three migration protocols are `nonisolated` for the same kind of reason: migrations run inside off-main launch tasks, and conformers are nonisolated value types confined to whatever isolation domain built them.
