# ``FernletLock``

The app-lock platform shim: passcode/biometric credentials, brute-force cooldowns, and the in-memory content key that unlocks Fernlet's sealed stores.

## Overview

FernletLock is the layer-6 "[S]" platform-shim target in the FernletKit package that owns Fernlet's app lock. Its single service, ``FernletLockService`` (an `@Observable @MainActor` final class conforming to ``FernletLockServicing``), is created once at app launch and injected into the SwiftUI environment; the presentation layer lives in the separate `FernletLockUI` module (setup, unlock, and the `fernletLockGate` view modifier), keeping this target presentation-free. Sealed feature code — the period tracker, worry box, journal, and progress photos — asks the service for the unlocked content key per operation and observes ``FernletLockState`` to know when to render, buffer, or refuse.

**An unlock covers exactly one screen.** Every credential entry point names the surface it speaks for, with no default: ``FernletLockService/configure(credential:grantingScope:)``, ``FernletLockService/unlock(passcode:for:)`` and ``FernletLockService/unlockWithBiometrics(for:)`` each grant a single ``FernletLockScope`` — `.privateHub` (the Private tab), `.progressPhotos` (the gym photo strip and its detail) or `.appLockSettings` (Settings → App lock) — and the grant rides *inside* the state as `.unlocked(scope:)` so it can never drift out of step with the unlock. Gated surfaces therefore ask ``FernletLockServicing/isUnlocked(for:)``, never `if case .unlocked`, and call ``FernletLockService/revokeUnlockOutside(_:)`` as they APPEAR so an arriving screen revokes a foreign unlock instead of inheriting one whose departure-side re-lock a covering sheet or scene transition may legitimately have suppressed. Two invariants hold underneath, and the P0a regressions in `FernletTests/SecureEnclaveWrapTests` pin their intersection: (1) the sealed-content key is released only to `.privateHub` — ``FernletLockService/contentKey(for:)`` is the decrypt seam, and `retainContentKey` keeps the key resident in memory for that scope alone, so a photo-strip or settings unlock recovers it purely as the act of verifying the passcode and then drops it (progress photos seal under `PrivateMediaKeyStore`'s own key; App-lock settings re-derive from the entered passcode); and (2) the Secure-Enclave wrap is established and round-trip-verified on every successful configure and on every LEGACY unlock regardless of scope (in the HARD-BOUND state it is simply unwrapped — it is already the authoritative copy, see the custody paragraph below), because that wrap protects the key at rest rather than the session. `hasResidentContentKey` exists solely so tests can distinguish "scrubbed" from "merely withheld" — it exposes a `Bool`, never a key.

The cryptographic scheme is deliberately small and is centralized in the module-internal `FernletLockCrypto` namespace. Configuring a credential derives a wrapping key from the passcode plus a random salt through the memory-hard scrypt KDF (CryptoSwift, the package's one external dependency; N=65536, r=8, p=1, run off the main actor via `Task.detached`), mints a random 256-bit content key, and seals the content key under the wrapping key with ChaChaPoly. What reaches the keychain is only: the salt, `SHA256(wrappingKey)` as the verifier (never the wrapping key itself), the wrapped content key, the credential kind, and the scrypt N — every item a ThisDeviceOnly, never-synchronized generic password under a ``LockKeychainKey`` account, and every write verified by status check plus read-back so a silently failing keychain cannot masquerade as configured state. While unlocked, the raw content key exists only in memory and is scrubbed on lock; sealed repositories derive per-column subkeys from it via HKDF (`ColumnCrypto` in `FernletCrypto`, whose derivation the crypto tests characterize directly). Verification accepts a legacy raw-key verifier from pre-split builds and migrates it to digest form in place on the next successful passcode entry. Biometric unlock keeps a second copy of the raw content key in a separate keychain item behind a `.biometryCurrentSet` access control, so iOS itself invalidates it when Face ID/Touch ID enrollment changes. Biometric unlock is additionally **PIN-before-biometrics**: it is refused (`FernletLockError.biometricNotAvailable`, which the unlock view turns into a silent passcode fallback) until one passcode success — ``FernletLockService/unlock(passcode:for:)`` or the initial ``FernletLockService/configure(credential:grantingScope:)`` — has happened in the current app process, mirroring iOS's own first-unlock-after-reboot rule. Two in-memory, never-persisted flags record that success (neither is ever set by a biometric success; `reset()` clears both): `passcodeUnlockedThisProcess` for a fully completed unlock, and `passcodeVerifiedThisProcess` for a correct passcode ENTRY, set at the verifier match before key recovery is attempted. The second exists because in the hard-bound state a dead enclave key makes every passcode unlock throw before the unlock tail, so gating on the first alone would strand the biometric bypass — the one surviving copy of the key, and the one that repairs the wrap. Either flag satisfies the fail-closed guard at the top of ``FernletLockService/unlockWithBiometrics(for:)``, which is the load-bearing enforcement, and the single computed policy `isBiometricUnlockAvailable` (enabled + usable biometry + a correct passcode this process) is what the lock UI's button and auto-prompt consult — the rule lives in that one property, and the planned duress phase extends it with one more conjunct there rather than at call sites. **Content-key custody is a two-state machine (hard Secure-Enclave binding, `Docs/Verifiability.md` §4/§6.1), discriminated by one thing: whether `LockKeychainKey.wrappedContentKey` exists.** In the **LEGACY** state it does, and it is authoritative: the enclave wrap maintained beside it (module-internal `SecureEnclaveContentKeyWrap`, a non-exportable enclave-resident P-256 key) is additive, preferred at unlock only when it provably equals the scrypt-unwrapped key, self-healed when stale or corrupt, and silently absent wherever no enclave exists — which is why SE-less hardware stays legacy permanently and behaves byte for byte as it always did. In the **HARD-BOUND** state the scrypt item is gone and `seWrappedContentKey` is the only recoverable copy: the salt and verifier still gate entry, so the passcode check and the brute-force ladder are unchanged, but recovery is an enclave unwrap, and the equality gate has nothing left to compare against. The sealed corpus plus a full keychain dump is then useless off-device *even with the passcode*.

The transition is **keep-old-until-verified** and lives in one place, `hardBindToSecureEnclaveIfVerified(contentKeyData:)`: it deletes the scrypt item only after re-reading the persisted enclave wrap from the keychain and proving it unwraps to exactly the authoritative key, and every other outcome — no enclave, no blob, a failed unwrap, mismatched bytes, a keychain error — returns having changed nothing, so the flip retries on the next unlock. `configure()` on enclave hardware is therefore born hard-bound (write the scrypt wrap, establish and verify the enclave wrap, delete the scrypt wrap), an existing install flips on its first unlock under this build, and `changeCredential()` in the hard-bound state recovers the key from the enclave and rewrites only the passcode gate — never resurrecting a scrypt-wrapped copy, which would silently undo the binding. The honest cost of the trade is a named error rather than a silent failure: if the enclave key is destroyed out from under a hard-bound install (Erase All Content and Settings, a Secure-Enclave reset, a restore onto other hardware), a *correct* passcode fails with `FernletLockError.contentKeyUnrecoverable` — "Sealed data can no longer be opened on this device. Reset app lock to continue." — leaving the attempt counter alone, since nothing about the entry was wrong. Four properties keep that error from being harsher than the state it describes. It is reserved for a **provable** loss: a keychain that would not answer (`errSecInteractionNotAllowed` while the device is locked, protected data unavailable) throws the retryable `FernletLockError.contentKeyTemporarilyUnavailable(status:)`, whose copy never mentions reset, and an undeterminable custody read throws `keychainFailure` before anything acts on a guess. It is tolerated for the two scopes that never receive the content key, so `.progressPhotos` (sealed under `PrivateMediaKeyStore`'s own intact key) and `.appLockSettings` (which hosts the reset) still unlock on the verifier match, holding no key. It is answerable from the screen that raises it — `FernletLockUI`'s unlock overlay grows a dedicated card, because `requiresReset` is deliberately never set here. And while biometrics are enabled it is not even final: the bypass item still holds the raw content key behind a `.biometryCurrentSet` data-protection ACL rather than inside the enclave (`Docs/Verifiability.md` §5), which is a documented residual *and* a real recovery path — a Face ID unlock recovers the key and re-establishes the wrap. The enclave stays the authority in that exchange: `maintainSecureEnclaveWrap` never overwrites an openable hard-bound blob (its one unauthenticated caller is the biometric path, and `storeVerified` is delete-then-add), and a bypass whose bytes the enclave contradicts is deleted rather than honored.

Brute-force protection is a keychain-persisted escalation ladder: every fourth failed passcode attempt starts a cooldown (60 s → 15 min → 1 h → 4 h), tracked against both the wall clock and the monotonic system uptime — the service takes the maximum of the two remainders, so rolling the clock forward cannot shorten a cooldown, while a detected reboot falls back to wall-clock accounting with an audit entry. Exhausting the ladder sets `requiresReset`, after which the only way forward is the destructive `reset()`, which deletes all lock keychain items, sweeps the journal/Worry Box device fallback keys under each of `sealedContentKeyServices` (the keys that seal two of the four sealed entities whenever the lock is closed), deletes the Secure Enclave wrap, purges the sealed encrypted CoreData entities through `PrivatePersistenceController` and rebuilds its store file, and abandons the content key (and with it all sealed content). That three-sweep key destruction is what makes `reset()` the one FULLY honest erase: no surviving key opens any byte the rebuild leaves behind.

In the package dependency DAG, FernletLock sits on the PROTECTED side of the S3 privacy wall. It depends downward on `FernletFoundation` (keychain helpers, `FernletLockError`, `FernletAuditLog`), `FernletDomainModel`, the sealed `PrivateStoreCore` (whose `PendingNarrativeBuffer` it drains and whose `PrivatePersistenceController` it purges on reset), `PrivateHealthStore` (it conforms to that module's narrow `PeriodLockContext` seam — a strictly one-directional edge; `PrivateHealthStore` never names FernletLock), and CryptoSwift. Because it can reach the sealed stores, the walled `AIProviders` and `CloudKitSync` targets must never grow a dependency edge to it — the wall's `DIAGNOSE_MISSING_TARGET_DEPENDENCIES=YES_ERROR` enforcement makes such an import a hard build error.

Concurrency: the target builds with `defaultIsolation(MainActor.self)`, so the service, its seam protocols (``FernletLockServicing``, ``FernletLockCryptoProviding``, ``FernletDateProviding``, ``FernletUptimeProviding``), and their system conformers are main-actor isolated; the pure crypto statics and free helpers are explicitly `nonisolated`. The two genuinely blocking operations — scrypt derivation and the LocalAuthentication-gated biometric keychain read — run off the main actor (a detached task and a global queue respectively). Every dependency of the service (date, uptime, crypto, keychain store/load closures, the biometric loader, the persistence controller) is constructor-injectable, which is how `FernletTests/FernletLockServiceTests` exercises cooldowns, clock tampering, and keychain failures deterministically. All failures surface as `FernletLockError` (defined in `FernletFoundation`), and every state transition is recorded through `FernletAuditLog`.
