# ``FernletLock``

The app-lock platform shim: passcode/biometric credentials, brute-force cooldowns, and the in-memory content key that unlocks Fernlet's sealed stores.

## Overview

FernletLock is the layer-6 "[S]" platform-shim target in the FernletKit package that owns Fernlet's app lock. Its single service, ``FernletLockService`` (an `@Observable @MainActor` final class conforming to ``FernletLockServicing``), is created once at app launch and injected into the SwiftUI environment; the presentation layer lives in the separate `FernletLockUI` module (setup, unlock, and the `fernletLockGate` view modifier), keeping this target presentation-free. Sealed feature code — the period tracker, worry box, journal, and progress photos — asks the service for the unlocked content key per operation and observes ``FernletLockState`` to know when to render, buffer, or refuse.

**An unlock covers exactly one screen.** Every credential entry point names the surface it speaks for, with no default: ``FernletLockService/configure(credential:grantingScope:)``, ``FernletLockService/unlock(passcode:for:)`` and ``FernletLockService/unlockWithBiometrics(for:)`` each grant a single ``FernletLockScope`` — `.privateHub` (the Private tab), `.progressPhotos` (the gym photo strip and its detail) or `.appLockSettings` (Settings → App lock) — and the grant rides *inside* the state as `.unlocked(scope:)` so it can never drift out of step with the unlock. Gated surfaces therefore ask ``FernletLockServicing/isUnlocked(for:)``, never `if case .unlocked`, and call ``FernletLockService/revokeUnlockOutside(_:)`` as they APPEAR so an arriving screen revokes a foreign unlock instead of inheriting one whose departure-side re-lock a covering sheet or scene transition may legitimately have suppressed. Two invariants hold underneath, and the P0a regressions in `Tests/FernletTests/SecureEnclaveWrapTests` pin their intersection: (1) the sealed-content key is released only to `.privateHub` — ``FernletLockService/contentKey(for:)`` is the decrypt seam, and `retainContentKey` keeps the key resident in memory for that scope alone, so a photo-strip or settings unlock recovers it purely as the act of verifying the passcode and then drops it (progress photos seal under `PrivateMediaKeyStore`'s own key; App-lock settings re-derive from the entered passcode); and (2) the Secure-Enclave wrap is established and round-trip-verified on every successful configure and on every LEGACY unlock regardless of scope (in the HARD-BOUND state it is simply unwrapped — it is already the authoritative copy, see the custody paragraph below), because that wrap protects the key at rest rather than the session. `hasResidentContentKey` exists solely so tests can distinguish "scrubbed" from "merely withheld" — it exposes a `Bool`, never a key.

The cryptographic scheme is deliberately small and is centralized in the module-internal `FernletLockCrypto` namespace. Configuring a credential derives a wrapping key from the passcode plus a random salt through the memory-hard scrypt KDF (CryptoSwift, the package's one external dependency; N=65536, r=8, p=1, run off the main actor via `Task.detached`), mints a random 256-bit content key, and seals the content key under the wrapping key with ChaChaPoly. What reaches the keychain is only: the salt, `SHA256(wrappingKey)` as the verifier (never the wrapping key itself), the wrapped content key, the credential kind, and the scrypt N — every item a ThisDeviceOnly, never-synchronized generic password under a ``LockKeychainKey`` account, and every write verified by status check plus read-back so a silently failing keychain cannot masquerade as configured state. The wrap carries a four-byte `FLW2` marker and authenticates a stable purpose as AAD, and since Phase 3 of the crypto-standardization plan that marker is **required on read**: an unprefixed wrap — the pre-domain generation, whose reader was the module's last `legacy-read` escape hatch — is refused by name as ``FernletLockError/contentKeyWrapFormatRetired`` rather than degrading into a bare ChaChaPoly authentication error that would read as "your sealed data is corrupt". All four callers that unwrap (`changeCredential`, `unlock`, `setBiometricEnabled`, `enrollRecoveryCustodian`) throw it before their first write or delete, so the refusal never costs a row; the Phase 2.5 migrator that converted such wraps went with the reader, because it converted *through* it. ``LockWrapFormatCensus`` **stays** — it classifies by the same marker byte the writer stamps, which is what lets the refusal say which format it found. While unlocked, the raw content key exists only in memory and is scrubbed on lock; sealed repositories derive per-column subkeys from it via HKDF (`ColumnCrypto` in `FernletCrypto`, whose derivation the crypto tests characterize directly). Verification accepts a legacy raw-key verifier from pre-split builds and migrates it to digest form in place on the next successful passcode entry. Biometric unlock keeps a second copy of the raw content key in a separate keychain item behind a `.biometryCurrentSet` access control, so iOS itself invalidates it when Face ID/Touch ID enrollment changes. Biometric unlock is additionally **PIN-before-biometrics**: it is refused (`FernletLockError.biometricNotAvailable`, which the unlock view turns into a silent passcode fallback) until one passcode success — ``FernletLockService/unlock(passcode:for:)`` or the initial ``FernletLockService/configure(credential:grantingScope:)`` — has happened in the current app process, mirroring iOS's own first-unlock-after-reboot rule. Two in-memory, never-persisted flags record that success (neither is ever set by a biometric success; `reset()` clears both): `passcodeUnlockedThisProcess` for a fully completed unlock, and `passcodeVerifiedThisProcess` for a correct passcode ENTRY, set at the verifier match before key recovery is attempted. The second exists because in the hard-bound state a dead enclave key makes every passcode unlock throw before the unlock tail, so gating on the first alone would strand the biometric bypass — the one surviving copy of the key, and the one that repairs the wrap. Either flag satisfies the fail-closed guard at the top of ``FernletLockService/unlockWithBiometrics(for:)``, which is the load-bearing enforcement, and the single computed policy `isBiometricUnlockAvailable` (enabled + usable biometry + a correct passcode this process) is what the lock UI's button and auto-prompt consult — the rule lives in that one property, and the planned duress phase extends it with one more conjunct there rather than at call sites. **Content-key custody is a two-state machine (hard Secure-Enclave binding, `Docs/Verifiability.md` §4/§6.1), discriminated by one thing: whether `LockKeychainKey.wrappedContentKey` exists.** In the **LEGACY** state it does, and it is authoritative: the enclave wrap maintained beside it (module-internal `SecureEnclaveContentKeyWrap`, a non-exportable enclave-resident P-256 key) is additive, preferred at unlock only when it provably equals the scrypt-unwrapped key, self-healed when stale or corrupt, and silently absent wherever no enclave exists — which is why SE-less hardware stays legacy permanently and behaves byte for byte as it always did. In the **HARD-BOUND** state the scrypt item is gone and `seWrappedContentKey` is the only recoverable copy: the salt and verifier still gate entry, so the passcode check and the brute-force ladder are unchanged, but recovery is an enclave unwrap, and the equality gate has nothing left to compare against. The sealed corpus plus a full keychain dump is then useless off-device *even with the passcode*. **Every decision that could destroy a key reads the keychain with `loadDistinguishingAbsence`, never with the collapsing presence read**: the launch state (an unreadable salt row boots `.locked`, not `.notConfigured`, and ``FernletLockService/refreshStateFromKeychain()`` re-derives it once protected data is available), ``FernletLockService/configure(credential:grantingScope:)`` (which refuses to mint over an existing OR unreadable lock), the duress salt's mint-on-absent, the recovery-material sweep inside `mintLockRecords`, and the Secure-Enclave wrap maintenance (which also treats a transient decrypt failure as retryable rather than as a rejected blob). A read that could not answer is never allowed to look like an absence, because every one of those branches deletes or overwrites the only copy of a key.

The transition is **keep-old-until-verified** and lives in one place, `hardBindToSecureEnclaveIfVerified(contentKeyData:)`: it deletes the scrypt item only after re-reading the persisted enclave wrap from the keychain and proving it unwraps to exactly the authoritative key, and every other outcome — no enclave, no blob, a failed unwrap, mismatched bytes, a keychain error — returns having changed nothing, so the flip retries on the next unlock. `configure()` on enclave hardware is therefore born hard-bound (write the scrypt wrap, establish and verify the enclave wrap, delete the scrypt wrap), an existing install flips on its first unlock under this build, and `changeCredential()` in the hard-bound state recovers the key from the enclave and rewrites only the passcode gate — never resurrecting a scrypt-wrapped copy, which would silently undo the binding. The honest cost of the trade is a named error rather than a silent failure: if the enclave key is destroyed out from under a hard-bound install (Erase All Content and Settings, a Secure-Enclave reset, a restore onto other hardware), a *correct* passcode fails with `FernletLockError.contentKeyUnrecoverable` — "Sealed data can no longer be opened on this device. Reset app lock to continue." — leaving the attempt counter alone, since nothing about the entry was wrong. Four properties keep that error from being harsher than the state it describes. It is reserved for a **provable** loss: a keychain that would not answer (`errSecInteractionNotAllowed` while the device is locked, protected data unavailable) throws the retryable `FernletLockError.contentKeyTemporarilyUnavailable(status:)`, whose copy never mentions reset, and an undeterminable custody read throws `keychainFailure` before anything acts on a guess. It is tolerated for the two scopes that never receive the content key, so `.progressPhotos` (sealed under `PrivateMediaKeyStore`'s own intact key) and `.appLockSettings` (which hosts the reset) still unlock on the verifier match, holding no key. It is answerable from the screen that raises it — `FernletLockUI`'s unlock overlay grows a dedicated card, because `requiresReset` is deliberately never set here. And while biometrics are enabled it is not even final: the bypass item still holds the raw content key behind a `.biometryCurrentSet` data-protection ACL rather than inside the enclave (`Docs/Verifiability.md` §5), which is a documented residual *and* a real recovery path — a Face ID unlock recovers the key and re-establishes the wrap. The enclave stays the authority in that exchange: `maintainSecureEnclaveWrap` never overwrites an openable hard-bound blob (its one unauthenticated caller is the biometric path, and `storeVerified` is delete-then-add), and a bypass whose bytes the enclave contradicts is deleted rather than honored.

**A duress PIN sits in front of every credential entry point (Phase 7).** One optional duress PIN with one chosen ``DuressMode`` — `.decoy` (non-destructive), `.silentWipe`, or `.recoveryLock` — is compared *before* the real verifier in ``FernletLockService/unlock(passcode:for:)``, ``FernletLockService/changeCredential(current:new:)`` and ``FernletLockService/setBiometricEnabled(_:passcode:)``. It has its OWN salt and verifier (``LockKeychainKey/duressSalt``, ``LockKeychainKey/duressVerifier``) rather than sharing the primary salt, because a re-key rewrites that salt and the app never holds the duress plaintext at that moment to recompute against — a shared salt would strand the duress PIN on the next passcode change. The derivation against the duress salt runs **unconditionally**: a random dummy salt is minted on demand and compared against a never-matching value when no duress PIN is configured, so an unlock always costs exactly two derivations and its latency cannot be timed to answer "does this device have a duress PIN?". In `unlock` the compare deliberately precedes the `requiresReset` and cooldown guards, so the duress PIN still works during a lockout — the moment coercion is likeliest — and it returns before `recordFailedAttempt`, so no counter ever sees it. In the other two entry points it is what stops a coerced PIN from re-keying the real lock or writing the real content key into the biometric bypass; symmetrically, a re-key whose NEW passcode equals the duress PIN is refused, because that would strand the real content key behind a passcode that always takes the duress branch, and a re-key that changes the credential KIND is refused while a duress PIN of an incompatible kind is configured — the lock renders exactly one entry surface with a hard-capped pad, so a 4-digit duress code cannot be typed at a `pin6` lock, and the own-salt design would otherwise carry the rows through untouched while ``FernletLockService/hasDuressConfigured`` kept reporting an armed response nobody could reach (``LockKeychainKey/duressKind`` is what makes that detectable).

**A duress PIN may never open `.appLockSettings`, and never costs less than a benign entry.** Settings → App lock is where the duress code is managed: a decoy session holding that scope could read "duress code set" and the armed response back to whoever was holding the phone, then change it, remove it, enrol a custodian of their own, or reset the lock. `handleDuress` therefore performs the configured response and then refuses that one surface — the caller raises the ordinary `invalidPasscode`, the attempt state is cleared exactly as a mistype's would be, and the `lock.failedAttempt` line carries the same cooldown level a mistype would have printed. The three non-`unlock` entry points revoke the settings unlock they were called from, for the same reason. That refusal is what makes ``FernletLockService/configureDuress(pin:mode:)``'s "real-PIN-gated by construction" premise true rather than assumed; `configureDuress`, ``FernletLockService/removeDuress()``, `enrollRecoveryCustodian` and ``FernletLockService/removeRecoveryCustodian()`` additionally refuse outright while `isDuressSessionActive`, so the property does not rest on a single check. And because a match used to return before the real verifier was ever derived, the decoy and recovery-lock paths spend one discarded derivation against the primary salt at the stored cost — an unlock costs two derivations whether it was benign, wrong, or duress, so the timing tells nothing either. (`.silentWipe` needs no balancing derivation: its re-mint already performs a second one.)

A match opens the **KEYLESS decoy**: `retainContentKey` is never called, so ``FernletLockService/contentKey(for:)`` returns nil even for `.privateHub` and every sealed surface renders empty — the decoy is the *absence* of a key, never a decoy key. It sets `isDuressSessionActive`, clears attempt state exactly as a successful unlock does, and emits the same `lock.released` audit line, so nothing distinguishes it afterwards; configuration and removal deliberately emit no audit event at all, since an event name reaching the unified log would itself disclose that a duress PIN exists. Nothing is persisted and nothing is deleted, so the decoy is fully reversible — the real passcode restores the real key. `isDuressSessionActive` survives ``FernletLockService/lock(reason:)`` on purpose and clears only on an act that PROVES the real credential — a real-passcode unlock, `configure()`, `reset()`, or ``FernletLockService/reestablishLocalUnlock(contentKey:credential:grantingScope:)`` (the tail of a ceremony the user physically ran). The duress-management calls do NOT clear it: they REFUSE while it is set, which is the stronger property and the one a coercer cannot walk around. in the non-destructive decoy the `.biometricBypass` row still holds the REAL content key, so both `isBiometricUnlockAvailable` (the UI policy) and the fail-closed guard in ``FernletLockService/unlockWithBiometrics(for:)`` (the guarantee) suppress biometrics for the whole duress session.

**`.silentWipe` puts a crypto-erase in front of that decoy.** Entering the duress PIN on a device configured for it deletes, synchronously and before anything is drawn, every key that can open a sealed byte here: the salt/verifier pair, the scrypt- and enclave-wrapped content keys, **the Secure-Enclave key itself**, **the `.biometricBypass` copy** (the raw content key behind Face ID — the copy a coercer can use with no PIN at all), the biometric-enabled flag, every duress and recovery row, the journal / Worry Box device fallback keys under `sealedContentKeyServices`, and the private-media keys under `mediaKeychainServices` (`com.fernlet.private-media`) — the three sweeps `reset()` needs to earn the word "crypto-erased", plus a fourth `reset()` deliberately does not need. Two of the four sealed entities are not sealed under the content key when the lock is closed, which is what the third sweep is for; the fourth is for progress (body) photos, meal and recipe photos and the sealed progress index, which are sealed under `PrivateMediaStore`'s OWN key — a key the lock never holds and the delete funnel deliberately KEEPS, so without it the sub-second claim was false for the photo corpus until the asynchronous purge caught up, and false forever if the process died first. (`reset()` does not sweep it: resetting the app lock is not a delete, and the photo corpus is not the lock's to erase.) That destruction *is* the guarantee, and it costs milliseconds because it is pure keychain deletion. A throwaway empty lock is then re-minted under the same PIN through the same `mintLockRecords` a real setup uses — without it the wiped device shows "set up app lock" on the next re-lock, which announces both that a duress PIN existed and that it fired — and the enclave hard-binding is re-established open-coded rather than through the audit-emitting helpers, because a `lock.seWrapEstablished` / `lock.hardBoundToSecureEnclave` pair landing beside a `lock.released` would be a legible "a lock was minted during that unlock" signature in a sysdiagnose. Only then does the decoy open, and only then does the injected fire-and-forget ``FernletLockService/duressPurgeHook`` run the durable purge of sealed rows and cloud copies through the app's one deletion funnel. Two honest limits: the re-minted lock makes the duress PIN the real passcode of a now-empty app, with no duress PIN left until the user sets a new one; and off-device ciphertext (sealed iCloud backups, heart-drop dead-drops) exists until the background purge or its own age-out reaches it — unopenable, but present. This is the ONE seam that destroys `com.fernlet.lock`; "Delete everything" still keeps it, and the call runs one way, so no non-duress path can reach here (`Docs/PrivacyWipeCoverage.md`).

**`.recoveryLock` is the opposite trade: destroy the local keys, keep the corpus.** It deletes the same salt/verifier pair, both wrapped content keys, the Secure-Enclave key, the biometric bypass and every duress row — so the coerced user can say truthfully that they cannot open the data, and mean it — while KEEPING three things the wipe destroys: ``LockKeychainKey/recoveryBlob``, the enrolled custodian's two public keys, and the journal / Worry Box device fallback keys. The first two are the way back; the third is kept because nothing in the recovery blob can restore it, so destroying it would be unrecoverable loss on the one response built to be recoverable (the rows it seals were never protected by the app lock — they are written while it is closed, by design). Nothing is re-minted and ``FernletLockService/duressPurgeHook`` never fires; the device presents the same keyless decoy every other mode does, and lands in `.notConfigured` on the next launch. Guards keep it from becoming an unannounced wipe, and they are about OPENABILITY rather than row presence — a distinction the first implementation got wrong in three places. It is unselectable until ``FernletLockService/hasRecoveryCustodian`` (all THREE rows, not just the public keys); if the material has vanished by the time the PIN is entered it degrades to the plain decoy rather than destroying anything; it is refused over a blob marked ``LockKeychainKey/recoveryBlobSuperseded``, the state a recovery-locked device reaches when its user sets up a NEW app lock before reaching their custodian (the blob is kept — it is the only route back to the pre-lock corpus — but it seals a key this lock no longer uses, so firing the response again would destroy the live key and the ceremony would hand back the superseded one); and an enrollment whose sealing this device's proximity identity has outlived is retired outright. That last one is not a duress path at all: the blob is sealed with this device's long-term key-agreement key mixed into the derivation and the custodian opens it with the live one, so an ordinary "Delete everything" — which regenerates the identity while deliberately keeping the app lock, the content key and the enrollment rows — makes it unopenable by anybody. ``LockKeychainKey/recoveryOwnerKeyAgreementPublicKey`` records the enrollment-time key so the app-side coordinator can notice, and ``FernletLockService/invalidateRecoveryCustodianForRotatedIdentity()`` retires the dead enrollment and rewrites an armed `.recoveryLock` to the non-destructive `.decoy`.

The blob is minted by ``FernletLockService/enrollRecoveryCustodian(passcode:signingPublicKey:keyAgreementPublicKey:ownKeyAgreementPublicKey:sealingContentKeyTo:)``, which is where the wall shows through: this module cannot seal, because sealing is X25519/HKDF/ChaChaPoly in ProximityKit and FernletLock must gain no edge to it. So the content key is released into a caller-supplied closure — the app-side `DuressRecoveryCoordinator` passes `IdentityService.seal(_:to:format:)` — and never crosses the return boundary; the sealing comes back and is persisted here, with the blob written LAST so a half-written enrollment always reads as "no custodian". Enrollment is duress-aware for a sharper reason than the other entry points: honoring a coerced PIN here would *export* the real content key to a device the coercer chose. The stored row is `SHA256("fernlet.lock.recovery.contentkey.v1" ‖ key) ‖ sealed`; only the sealed half ever leaves the device, and the digest half is what lets ``FernletLockService/reestablishLocalUnlock(contentKey:credential:grantingScope:)`` REFUSE a returned key that is not the one the corpus is sealed under — turning a wrong answer into a named error instead of a silent, permanent re-lock around bytes that open nothing. That call rebuilds the lock through the same `mintLockRecords` a fresh setup uses and emits the same `lock.configured` line, so a sysdiagnose cannot be read as "a recovery happened here". Two ordering rules protect the route in the meantime: a `configure()` on a device that ``FernletLockService/isAwaitingCustodianRecovery`` keeps the recovery rows (a recovery-locked device shows "set up app lock", and tapping it must not destroy the only way back), and ``FernletLockService/removeRecoveryCustodian()`` refuses while `.recoveryLock` is still armed. The ceremony itself — in-person QR mutual auth over `ProximityVerifyQR`, the blob sent on a sealed wire, the reply signed by the enrolled custodian — lives entirely in the app target, and there is no cloud recovery route of any kind.

Brute-force protection is a keychain-persisted escalation ladder: every fourth failed passcode attempt starts a cooldown (60 s → 15 min → 1 h → 4 h), tracked against both the wall clock and the monotonic system uptime — the service takes the maximum of the two remainders, so rolling the clock forward cannot shorten a cooldown, while a detected reboot falls back to wall-clock accounting with an audit entry. Exhausting the ladder sets `requiresReset`, after which the only way forward is the destructive `reset()`, which deletes all lock keychain items, sweeps the journal/Worry Box device fallback keys under each of `sealedContentKeyServices` (the keys that seal two of the four sealed entities whenever the lock is closed), deletes the Secure Enclave wrap, purges the sealed encrypted CoreData entities through `PrivatePersistenceController` and rebuilds its store file, and abandons the content key (and with it all sealed content). That three-sweep key destruction is what makes `reset()` the one FULLY honest erase: no surviving key opens any byte the rebuild leaves behind.

In the package dependency DAG, FernletLock sits on the PROTECTED side of the S3 privacy wall. It depends downward on `FernletFoundation` (keychain helpers, `FernletLockError`, `FernletAuditLog`), `FernletDomainModel`, the sealed `PrivateStoreCore` (whose `PendingNarrativeBuffer` it drains and whose `PrivatePersistenceController` it purges on reset), `PrivateHealthStore` (it conforms to that module's narrow `PeriodLockContext` seam — a strictly one-directional edge; `PrivateHealthStore` never names FernletLock), and CryptoSwift. Because it can reach the sealed stores, the walled `AIProviders` and `CloudKitSync` targets must never grow a dependency edge to it — the wall's `DIAGNOSE_MISSING_TARGET_DEPENDENCIES=YES_ERROR` enforcement makes such an import a hard build error.

Concurrency: the target builds with `defaultIsolation(MainActor.self)`, so the service, its seam protocols (``FernletLockServicing``, ``FernletLockCryptoProviding``, ``FernletDateProviding``, ``FernletUptimeProviding``), and their system conformers are main-actor isolated; the pure crypto statics and free helpers are explicitly `nonisolated`. The two genuinely blocking operations — scrypt derivation and the LocalAuthentication-gated biometric keychain read — run off the main actor (a detached task and a global queue respectively). Every dependency of the service (date, uptime, crypto, keychain store/load closures, the biometric loader, the persistence controller) is constructor-injectable, which is how `Tests/FernletTests/FernletLockServiceTests` exercises cooldowns, clock tampering, and keychain failures deterministically. All failures surface as `FernletLockError` (defined in `FernletFoundation`), and every state transition is recorded through `FernletAuditLog`.
